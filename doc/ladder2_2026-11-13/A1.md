Patterns seen in more than one repo:
- Package-level mutable state written from handler/connection goroutines with no lock: A-Blockchain-With-Golang main.go:65,:74; go-chi-CRUD controllers/article.go:18,:46; Complete_GO_Blockchain core/server.go:25,:314; CSRF-Golang-Killer-Project db/db.go:16,:21; any-website-sitemap-crawler main.go:128. Five of 23 repos. `guard.Guarded` (TB-GUARD-001) is the fix every time; a `go vet`-style check is not available, so the reviewer should grep for `^var .* = make(map` and `^var .* \[\]` in handler packages.
- Bounded parallelism by token channel + WaitGroup + shared results: any-website-sitemap-crawler main.go:111; AI-Code-Bundler reading.go:74; Git-Secrets-Scanner task.go:83. All three reinvent TB-PAR-001/TB-POOL-001; two of three lose results or errors.
- HTTP client gateway with the body-close/err-check order wrong or missing timeouts: Consuming-Pexels-API main.go:113; AI-Code-Bundler review.go:43-50; BSIDES llm/*.go (ctx only). Argues for `httpx.DoJSON` landing early in the T6 wave.
- `rand.Seed(time.Now().Unix())` per call: sitemap crawler main.go:42, Pexels main.go:178. Dead since go1.20; `math/rand/v2`.
- `log.Fatal`/`log.Panic` inside library code: AI-Code-Bundler review.go:46; Complete_GO_Blockchain everywhere; CSRF middleware.go:24,:66; BulletProof utils/logger/logger.go:5. Our rule "a library function never panics on input" is confirmed as the thing these repos get wrong most often.
- Middleware chains: BulletProof routes.go:33-40 (chi), CSRF middleware.go:16 (alice), go-chi-CRUD main.go:15. Order differs in each; `httpx.Chain` must document the canonical order.

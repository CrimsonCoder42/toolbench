=== package guard
package guard // import "github.com/CrimsonCoder42/toolbench/guard"

Package guard keeps shared mutable state behind a stated guard
(.claude/rules/go-concurrency.md, rule 8), in the two shapes Effective Go names:
a value behind its own mutex (Guarded), and a goroutine that owns its state and
serves requests sent on a channel (Confine, "share memory by communicating"),
plus one lock per key (Keyed, lock striping) for callers that must not wait on
each other's keys.

ID short form: GUARD (IDs are TB-GUARD-NNN).

Exports:

    TB-GUARD-001  Guarded  a value of type T behind its own mutex: Do runs fn on it under the lock, Load copies it
    TB-GUARD-002  Confine  serves requests on one goroutine that owns the state, until reqs closes or ctx is done
    TB-GUARD-003  Keyed  one lock per key (lock striping): Do runs fn while no other Do on that key runs; entries leave at refcount zero
    TB-GUARD-004  NewKeyed  an empty Keyed with options applied (the zero value is ready without it)
    TB-GUARD-005  KeyedOption  configures NewKeyed
    TB-GUARD-006  WithMaxKeys  bounds the distinct keys a Keyed holds or waits on at once (default 10 000)
    TB-GUARD-007  DefaultMaxKeys  the key bound of Keyed when WithMaxKeys is not given: 10 000
    TB-GUARD-008  ErrKeys  the sentinel for a new key when the key bound is full, or a key not equal to itself

CONSTANTS

const DefaultMaxKeys = 10_000
    DefaultMaxKeys is the bound on distinct keys a Keyed holds or waits on at
    once when WithMaxKeys is not passed (or n <= 0): 10 000, the same default
    as ratelimit.DefaultMaxKeys. Entries leave when their last caller does,
    so this bounds concurrent use, not history.

    ID: TB-GUARD-007 Pattern: bounded table (default bound) Authority:
    pkg.go.dev golang.org/x/sync/singleflight, "type Group" (the keyed-table
    shape, there unbounded) Tags: lock, per-key, bound, keys, default


VARIABLES

var ErrKeys = errors.New("guard: key bound full")
    ErrKeys is returned by Keyed.Do and Keyed.TryDo when a new key arrives and
    the key bound (WithMaxKeys) is full, or when the key is not equal to itself
    (a NaN) and so could never be removed from the table. It is always wrapped
    (the count of keys, or the reason); match it with errors.Is.

    ID: TB-GUARD-008 Pattern: sentinel error Authority: pkg.go.dev errors,
    "func Is" Tags: errors, sentinel, lock, per-key, bound, keys


FUNCTIONS

func Confine[S any](ctx context.Context, state S, reqs <-chan func(*S)) (S, error)
    Confine makes the calling goroutine the only owner of state: it receives
    requests from reqs and runs each one, in arrival order, with a pointer to
    its copy of state, until reqs is closed, ctx is done or a request panics,
    and then returns the final state. A request that needs an answer closes over
    its own reply channel. A nil reqs is handled as a closed one; a nil request
    is skipped; a nil ctx is context.Background(). Run it as go func() { s,
    err = guard.Confine(ctx, s0, reqs) }() for a separate owner goroutine;
    that goroutine ends when Confine returns.

    The *S a request receives is valid only while it runs (keeping it is a data
    race). The returned S is a shallow copy of the final state.

    ID: TB-GUARD-002 Pattern: confinement (one goroutine owns the state;
    others send it requests) Authority: Effective Go, go.dev, "Concurrency",
    "Share by communicating" Authority: Cox-Buday, Concurrency in Go, O'Reilly,
    2017, ch.4, "Confinement" Goroutines: none; the loop runs on the caller's
    goroutine and has returned when Confine returns Cancel: ctx done: returns
    at once when waiting, or after the request it has received finishes Cancel:
    a request already received runs to completion; no request is received
    after that Errors: nil when reqs is closed (every request sent ran) or nil;
    context.Cause(ctx) when ctx is done Errors: a panic in a request stops the
    loop: the state as the panic left it and a *panics.PanicError Blocking:
    until reqs is closed, ctx is done or a request panics; senders block
    until the owner receives Tags: concurrency, confinement, channel, owner,
    shared-state, generic


TYPES

type Guarded[T any] struct {
	// Has unexported fields.
}
    Guarded is a value of type T behind its own mutex: the only ways to reach
    the value are Do, which runs a function on it under the lock, and Load,
    which returns a copy taken under the lock. Every write made in one Do is
    visible to every later Do and Load (the Go memory model's rule for Unlock
    before Lock).

    The zero value is ready to use and holds T's zero value. A Guarded holds a
    sync.Mutex: it must not be copied after first use (go vet copylocks reports
    a copy); pass *Guarded[T] or keep it in a struct used by pointer.

    ID: TB-GUARD-001 Pattern: mutual exclusion (a mutex beside the value it
    guards) Authority: The Go Memory Model, go.dev, "Synchronization", "Locks"
    Authority: Effective Go, go.dev, "Concurrency", "Share by communicating"
    Goroutines: none; Do's fn runs on the caller's goroutine Blocking:
    Do and Load wait for the mutex (not cancellable, like sync.Mutex.Lock);
    keep fn short Tags: concurrency, mutex, lock, shared-state, generic

func (g *Guarded[T]) Do(fn func(*T))
    Do locks g, calls fn with a pointer to the guarded value and unlocks g when
    fn returns. A nil fn is a no-op.

    The pointer is valid only until fn returns: keeping it, sending it elsewhere
    or handing it to a goroutine and using it after fn returns is a data race
    this type cannot prevent; the same holds for maps, slices and pointers
    inside T. fn must not call Do or Load on the same g: sync.Mutex is not
    re-entrant and that call deadlocks. A panic in fn is not recovered: g is
    unlocked first (deferred), then the panic continues up the caller's stack,
    so the next Do does not deadlock; the value keeps whatever fn wrote before
    panicking. Wrap the call in panics.Try to turn that panic into an error.

func (g *Guarded[T]) Load() T
    Load returns a copy of the guarded value, taken under the lock. The copy
    is shallow: a map, slice, pointer or channel inside T still refers to the
    guarded data, and reading or writing through it outside Do is a data race.
    For such a T, copy deeply inside Do instead.

type Keyed[K comparable] struct {
	// Has unexported fields.
}
    Keyed is a set of locks, one per key (lock striping): Do runs fn while no
    other Do or TryDo with the same key runs, and callers on distinct keys never
    wait on each other. Entries are reference-counted (holders plus waiters) and
    removed when the last one leaves, so the table never grows past the keys
    in use and nothing sweeps it; WithMaxKeys bounds the distinct keys held or
    waited on at once (ErrKeys when full). Every write made in one fn is visible
    to the next fn on the same key (the Go memory model's rule for a buffered
    channel: the holder's receive is synchronized before the next holder's send
    completes).

    The zero value is ready to use (the bound is DefaultMaxKeys); NewKeyed only
    applies options. A Keyed holds a sync.Mutex: it must not be copied after
    first use (go vet copylocks reports a copy); pass *Keyed[K].

    Unlike Guarded.Do, a panic in fn is recovered here (Do has an error result)
    and returned as a *panics.PanicError with the key released. The locks are
    not re-entrant: fn calling Do on the same key deadlocks (as sync.Mutex);
    on different keys the caller orders the keys to avoid an A/B-B/A deadlock.

    ID: TB-GUARD-003 Pattern: lock striping (one lock per key; mutual exclusion
    per key) Authority: The Go Memory Model, go.dev, "Synchronization", "Locks"
    and "Channel communication" Authority: pkg.go.dev sync, "type Mutex", "func
    (*Mutex) TryLock" Authority: Cox-Buday, Concurrency in Go, O'Reilly, 2017,
    ch.3, "The sync Package", "Mutex and RWMutex" Goroutines: none; fn runs on
    the caller's goroutine; no sweeper Cancel: Do: ctx done while waiting for
    the key returns context.Cause(ctx) and leaves no entry; fn, once started, is
    not interrupted Errors: Do and TryDo: fn's error unchanged; ErrKeys (wrapped
    with the count) when the bound is full or the key is not equal to itself;
    a panic in fn as *panics.PanicError Blocking: Do waits for the key or ctx;
    TryDo never blocks; the table mutex is held for O(1) per call Tags:
    concurrency, mutex, lock, striping, per-key, shared-state, bounded, generic

func NewKeyed[K comparable](opts ...KeyedOption) *Keyed[K]
    NewKeyed returns an empty Keyed with opts applied (nil options are ignored).
    It exists only to apply options: the zero value of Keyed is ready to use
    with the defaults.

    ID: TB-GUARD-004 Pattern: lock striping (constructor) Authority: Pike,
    "Self-referential functions and the design of options", command center
    (blog), 2014 Tags: concurrency, lock, striping, per-key, constructor,
    generic

func (g *Keyed[K]) Do(ctx context.Context, key K, fn func() error) error
    Do waits until no other Do or TryDo holds key (or ctx is done),
    runs fn, releases key and returns fn's error. A ctx already done returns
    context.Cause(ctx) before touching the table; ctx done while waiting
    returns context.Cause(ctx) and the waiter's entry is dropped (the holder is
    unaffected). A new key when the table holds WithMaxKeys keys, or a key not
    equal to itself (a NaN), is refused with ErrKeys. A panic in fn is returned
    as a *panics.PanicError (errors.Is(err, panics.ErrPanic)) with the key
    released; this differs from Guarded.Do, which has no error result and lets
    the panic propagate. A nil fn is a no-op that returns nil without taking the
    key; a nil ctx is context.Background().

func (g *Keyed[K]) Len() int
    Len reports how many distinct keys are held or waited on right now; 0 when g
    is idle. It is the size of the table, which WithMaxKeys bounds.

func (g *Keyed[K]) TryDo(key K, fn func() error) (ran bool, err error)
    TryDo runs fn under key if the key is free right now and reports whether
    it ran; it never waits. ran is false, with a nil error, when another Do or
    TryDo holds key; this is sync.Mutex.TryLock's shape, and as its doc says,
    needing it is often a sign of a deeper problem: prefer Do with a ctx.
    ErrKeys, panics and a nil fn are as for Do (a nil fn reports (true, nil)
    without taking the key).

type KeyedOption func(*keyedConfig)
    KeyedOption configures NewKeyed. The zero value (a nil KeyedOption) is
    ignored. It carries the type's name so that an option for Guarded or
    Confine, should one ever exist, cannot be confused with it.

    ID: TB-GUARD-005 Pattern: functional options Authority: Pike,
    "Self-referential functions and the design of options", command center
    (blog), 2014 Tags: options, configuration, lock, per-key

func WithMaxKeys(n int) KeyedOption
    WithMaxKeys bounds how many distinct keys a Keyed holds or waits on at once.
    The default, and n <= 0, is DefaultMaxKeys (10 000). A Do or TryDo on a new
    key when the bound is full is refused with ErrKeys; a key already in the
    table is never refused.

    ID: TB-GUARD-006 Pattern: functional options; bounded table Authority:
    Pike, "Self-referential functions and the design of options", command center
    (blog), 2014 Tags: options, lock, per-key, bound, keys

=== package lifecycle
package lifecycle // import "github.com/CrimsonCoder42/toolbench/lifecycle"

Package lifecycle starts the parts of a process in order and stops them
gracefully, in reverse, within a drain deadline: the run group of a main
function. Group.Run calls each Component's Start in the order it was added,
waits until its ctx is done (a signal, through WithNotify), then calls the
Stop of every started component in reverse order under one grace deadline,
as net/http Server.Shutdown drains with a deadline. A Start that fails stops
the components already started, in reverse. A Component.Run (a server's Serve,
a consumer loop) runs on its own goroutine once every Start has returned; the
first Run to return, nil or error, begins the shutdown as ctx being done does,
and the remaining Runs are waited for within the same grace period. Run is the
one-component form: a blocking start (a server's Serve) and the stops that end
it. Group.Live and Group.Ready aggregate the components' health checks under the
caller's ctx; Ready is false until every Start has returned and from the instant
shutdown begins, so a probing load balancer stops routing while the components
drain.

Stop errors are all returned (errors.Join), each naming its component.
A component that has not stopped when the grace period ends is named in
an ErrStopTimeout error and Run returns at once: the process is about
to exit, and a stuck Stop must not hold it (The Twelve-Factor App, "IX.
Disposability"). A panic in Start, Stop or the notify hook is recovered
and returned as panics.ErrPanic. Nothing here panics on input: a nil ctx is
context.Background(), a non-positive grace is DefaultGrace, a nil Start or Stop
does nothing, a second Run is ErrClosed. The package never imports os/signal:
the caller passes signal.NotifyContext through WithNotify.

ID short form: LIFE (IDs are TB-LIFE-NNN).

Exports:

    TB-LIFE-001  Stopper         a function that stops one component within the deadline of its ctx
    TB-LIFE-002  Run             runs a blocking start until it returns or ctx is done, then the stops in reverse
    TB-LIFE-003  Component       one part of a process: a Name, a Start and a Stop
    TB-LIFE-004  Group           a run group: ordered start, reverse-order stop, drain deadline
    TB-LIFE-005  Option          a functional option for Group.Run
    TB-LIFE-006  WithGrace       the drain deadline for every Stop together (default DefaultGrace)
    TB-LIFE-007  WithClock       the clock that measures the grace period (default clock.Real())
    TB-LIFE-008  WithNotify      the shutdown hook, for example signal.NotifyContext (default none)
    TB-LIFE-009  ErrClosed       returned by Run and Add once a Group has been run
    TB-LIFE-010  ErrStopTimeout  the grace period ended before every component stopped
    TB-LIFE-011  DefaultGrace    the grace period used when none (or a non-positive one) is given: 30s
    TB-LIFE-012  Group.Live            Group.Live: every component's liveness check, one at a time, errors joined and named
    TB-LIFE-013  Group.Ready           Group.Ready: ErrNotReady while starting or stopping, else every readiness check
    TB-LIFE-014  ErrNotReady     matched by every error Group.Ready returns (starting, shutting down, a failing check)

CONSTANTS

const DefaultGrace = 30 * time.Second
    DefaultGrace is the grace period when none, or a non-positive one, is given:
    the time every Stop together has to return once shutdown begins. 30s is the
    default termination grace period of common process managers (Kubernetes
    terminationGracePeriodSeconds) and faktory's ShutdownTimeout is 25s;
    choose one shorter than the manager's, which sends SIGKILL when it runs out.

    ID: TB-LIFE-011 Pattern: graceful shutdown (drain deadline) Authority: The
    Twelve-Factor App, "IX. Disposability" (https://12factor.net/disposability)
    Tags: lifecycle, shutdown, deadline, default


VARIABLES

var ErrClosed = errors.New("lifecycle: group already run")
    ErrClosed is returned by Group.Run and Group.Add once Run has been called
    on the Group: a Group runs once, as an http.Server is not reused after
    Shutdown. Match it with errors.Is.

    ID: TB-LIFE-009 Pattern: sentinel error Authority: pkg.go.dev net/http,
    "func (*Server) Shutdown" ("Once Shutdown has been called on a server,
    it may not be reused") Tags: lifecycle, error, closed

var ErrNotReady = errors.New("lifecycle: not ready")
    ErrNotReady is matched (errors.Is) by every error Group.Ready returns:
    before every Start has returned nil (also before Run is called and after
    a Start failed), from the instant shutdown begins, and when a Ready check
    fails (the check errors are wrapped under it). A caller exposing readiness
    over HTTP maps it to 503.

    ID: TB-LIFE-014 Pattern: sentinel error (readiness) Authority: Microsoft
    Azure Architecture Center, "Health Endpoint Monitoring pattern", "Example
    > Endpoint behavior" ("Return 200 (OK) when the application can serve
    requests, or 503 (Service Unavailable) when a required check fails") Tags:
    lifecycle, error, health, readiness

var ErrStopTimeout = errors.New("lifecycle: grace period ended before every component stopped")
    ErrStopTimeout is matched (errors.Is) by the error Run returns when the
    grace period ends before every Stop has returned. The message names the
    component still stopping and every component whose Stop was not called.
    It is also the cause (context.Cause) of the ctx given to the Stop that was
    still running.

    ID: TB-LIFE-010 Pattern: sentinel error (drain deadline exceeded) Authority:
    pkg.go.dev net/http, "func (*Server) Shutdown" ("If the provided context
    expires before the shutdown is complete, Shutdown returns the context's
    error") Tags: lifecycle, error, shutdown, deadline


FUNCTIONS

func Run(ctx context.Context, grace time.Duration, start func(context.Context) error, stops ...Stopper) error
    Run calls start(ctx) on its own goroutine and waits until start returns or
    ctx is done. Then it calls the stops in reverse order (stops[len-1] first),
    one at a time, and waits for start to return, all within grace (a grace <=
    0 is DefaultGrace), measured on the real clock. Each stop gets a ctx that
    keeps ctx's values, is not cancelled by ctx and is cancelled with cause
    ErrStopTimeout when grace ends; when grace ends first, Run returns at once
    with an ErrStopTimeout error naming the stop (or "start") still running and
    the stops never called. A typical start is an http.Server's ListenAndServe
    and a typical stop its Shutdown.

    start's error is returned, wrapped as "lifecycle: start: ...", except, after
    ctx is done, an error that matches ctx.Err() or context.Cause(ctx) (start
    returning because it was cancelled is a clean stop); http.ErrServerClosed
    is returned like any other error, so filter it in start. A start that
    returns before ctx is done (nil or an error) begins the shutdown at once.
    A nil start waits for ctx; a nil stop is skipped; a nil ctx is
    context.Background(). If ctx is done before the call, start and the stops
    are not called and Run returns context.Cause(ctx). For several components
    started in order, use Group.

    ID: TB-LIFE-002 Pattern: graceful shutdown (drain with deadline,
    reverse-order stop) Authority: pkg.go.dev net/http, "func (*Server)
    Shutdown" Authority: The Twelve-Factor App, "IX. Disposability"
    (https://12factor.net/disposability) Goroutines: one for start, one per
    stop (one at a time); all have exited when Run returns, except those still
    running when grace ends (named in the error; D-027): a stuck stop leaves
    one, a stuck start at most two (start's own and the one waiting for it),
    each ending when that call returns Cancel: ctx done before the call: nothing
    runs, the cause is returned; while start runs: the shutdown begins Errors:
    start's error and every stop error, errors.Join, each named; ErrStopTimeout;
    a panic is panics.ErrPanic Blocking: until start has returned and every stop
    has returned, or grace has ended Tags: lifecycle, shutdown, graceful, drain,
    server


TYPES

type Component struct {
	Name  string
	Start func(ctx context.Context) error
	Stop  Stopper
	Run   func(ctx context.Context) error
	Live  func(ctx context.Context) error
	Ready func(ctx context.Context) error
}
    Component is one part of a process that Group starts and stops: a database
    pool, a cache, a consumer, a server. Start is called once, in Add order, and
    returns when the component is up (nil) or could not be started (an error);
    it does not block for the component's lifetime. Work that outlives Start
    runs either in Run (below) or on goroutines Start spawns and Stop ends
    and waits for: derive those from context.WithoutCancel(ctx) so that Stop,
    in reverse order, ends them rather than the signal. Stop is called once, in
    reverse order, only if Start returned nil. A nil Start is a component that
    needs no start; a nil Stop one that needs no stop. Name is used in errors;
    empty is "component <n>" (n counts from 1 in Add order). The zero value is a
    component that does nothing.

    Run is the component's blocking run-time work (a server's Serve, a consumer
    loop). Group.Run calls it on its own goroutine once every Start has returned
    nil, with a context derived from the run ctx. The first Run to return,
    nil or error, begins the shutdown exactly as ctx being done does (oklog/run:
    "When the first actor returns, all others are interrupted"; errgroup:
    the first error cancels the Context); its context is cancelled when shutdown
    begins, before the first Stop, with a cause naming who ended the group.
    A Run that must drain in order ignores its ctx and lets its Stop end it,
    as http.Server's Serve returns when Shutdown is called. After the stops,
    Group.Run waits for every Run within the same grace period. A nil Run is a
    component with no run-time work.

    Live and Ready are health checks: Group.Live and Group.Ready call them on
    the caller's goroutine with the caller's ctx and return nil (healthy) or an
    error. Live answers "is this process alive" regardless of the start/stop
    state; Ready answers "can this component serve" and is only consulted while
    the group is running. A nil check is always healthy.

    Run, Live and Ready were added on 2026-11-13: keyed literals (the documented
    form) are unchanged; an unkeyed Component{name, start, stop} literal no
    longer compiles.

    ID: TB-LIFE-003 Pattern: graceful shutdown (ordered start, reverse-order
    stop, run-time failure seam, health checks) Authority: pkg.go.dev net/http,
    "func (*Server) Shutdown", "func (*Server) RegisterOnShutdown" Authority:
    pkg.go.dev golang.org/x/sync/errgroup, "func WithContext" ("canceled the
    first time a function passed to Go returns a non-nil error") Authority:
    Microsoft Azure Architecture Center, "Health Endpoint Monitoring pattern",
    "Solution" ("Deep checks verify the application and the dependencies
    required to serve requests. Use them for readiness signals") Tags:
    lifecycle, component, start, stop, run, health

type Group struct {
	// Has unexported fields.
}
    Group is a run group with ordered start and reverse-order stop. Add the
    components, then Run starts them in Add order, runs each component's Run on
    its own goroutine, waits until ctx (or the WithNotify context) is done or
    the first Run returns, and stops the started ones in reverse order within
    the grace period, then waits for the remaining Runs within the same period.
    Live and Ready aggregate the components' health checks; Ready is false until
    every Start has returned and from the instant shutdown begins. A Group runs
    once. The zero value is ready to use; a Group must not be copied after first
    use. Add, Run, Live and Ready are safe for concurrent use.

    ID: TB-LIFE-004 Pattern: graceful shutdown (run group, ordered start, first
    failure ends all, reverse-order stop, drain deadline) Authority: pkg.go.dev
    net/http, "func (*Server) Shutdown" Authority: pkg.go.dev os/signal,
    "func NotifyContext" Authority: pkg.go.dev golang.org/x/sync/errgroup,

    returns; D-027) Cancel: ctx done before every Start was called: the rest are
    not started, the started ones are stopped, Run returns the cause; after:

func (g *Group) Add(c Component) error
    Add appends c to the components Run starts, after those already added.
    It returns ErrClosed, and c is not added, once Run has been called.

func (g *Group) Live(ctx context.Context) error
    Live reports whether the process is alive: it calls the Live check of every
    added component, one at a time on the caller's goroutine, each with ctx,
    in Add order, and returns nil or their errors joined, each wrapped
    "lifecycle: live <name>: ...". It is independent of the start/stop state:
    it answers before Run, while the components start, while they run,
    while they stop and after Run returned, so a check must be able to answer
    before its Start. Checks run one at a time (this package does not fan out);
    the caller sets the deadline with ctx and caches the result where probes
    are frequent: nothing is cached here. A nil ctx is context.Background().
    Safe for concurrent use with Add, Run and Ready.

    ID: TB-LIFE-012 Pattern: health endpoint monitoring (liveness check)
    Authority: Microsoft Azure Architecture Center, "Health Endpoint Monitoring
    pattern", "Solution" ("Bound each dependency check with a timeout";
    "health signals that load balancers and traffic routers can use to direct
    requests to healthy instances") Goroutines: none; the checks run on the
    caller's goroutine Cancel: ctx done: the remaining checks are not called and
    context.Cause(ctx) is joined with the errors so far Errors: every failing
    check, errors.Join, each wrapped with the component's name; a panic in a
    check is panics.ErrPanic Blocking: for as long as the checks take, one after
    another; bound it with ctx Tags: lifecycle, health, liveness, check

func (g *Group) Ready(ctx context.Context) error
    Ready reports whether the process can serve. It returns an error matching
    ErrNotReady, without calling any check, before every Start has returned nil
    (also before Run is called, and after a Start failed) and from the instant
    shutdown begins (ctx done, or the first Run returned): the state flips
    before the run ctx is cancelled and before the first Stop is called, so a
    load balancer that probes stops routing while the components drain; it stays
    not ready after Run returned. While the group is running it calls the Ready
    check of every added component as Live does, and returns nil or ErrNotReady
    wrapping their errors joined, each "lifecycle: ready <name>: ...". The
    state is read once, before the checks. A nil ctx is context.Background().
    Safe for concurrent use with Add, Run and Live.

    ID: TB-LIFE-013 Pattern: health endpoint monitoring (readiness check;
    false while starting and from the start of shutdown) Authority: Microsoft
    Azure Architecture Center, "Health Endpoint Monitoring pattern", "Example >
    Endpoint behavior" ("Readiness ... Check initialization and both required
    dependencies ... 503 (Service Unavailable) when a required check fails.
    Bound each dependency check with a timeout") Authority: The Twelve-Factor
    App, "IX. Disposability" ("ceasing to listen on the service port ...,
    allowing any current requests to finish, and then exiting") Goroutines:
    none; the checks run on the caller's goroutine Cancel: ctx done:
    the remaining checks are not called and context.Cause(ctx) is joined under
    ErrNotReady Errors: ErrNotReady, alone while starting or stopping, wrapping
    every failing check (each named) while running; a panic in a check is
    panics.ErrPanic Blocking: for as long as the checks take, one after another;
    bound it with ctx; never while starting or stopping Tags: lifecycle, health,
    readiness, check, shutdown

func (g *Group) Run(ctx context.Context, opts ...Option) error
    Run starts the components, runs them and stops them; it returns when every
    started component has stopped or the grace period has ended.

    Start: with WithNotify, notify(ctx) is called first and its context replaces
    ctx. Then each Start is called on Run's goroutine with ctx, in Add order;
    component k+1 starts only after Start k returned nil. If Start k returns an
    error or panics, components k+1.. are not started and k-1..1 are stopped
    in reverse; k is not stopped (a failed Start cleans up after itself, as a
    constructor that returns an error). If ctx is done before Start k is called,
    the same happens to 1..k-1 and Run returns context.Cause(ctx).

    Run: once every Start has returned nil, Ready becomes true and each non-nil
    Component.Run is called on its own goroutine with the run ctx, a child of
    ctx. Run then waits for ctx to be done or for the first Component.Run to
    return, nil or error: either begins the shutdown. The run ctx is cancelled
    when shutdown begins, before the first Stop, with a cause naming the
    component that ended the group (or ctx's own cause).

    Stop: Ready becomes false, then the Stop of every started component is
    called in reverse order, one at a time, each with a ctx that keeps ctx's
    values, is not cancelled by ctx, and is cancelled with cause ErrStopTimeout
    when the grace period (WithGrace, measured on WithClock) ends. The stop
    ctx has no Deadline, since the clock may be fake. After the stops, every
    Component.Run not yet returned is waited for, one at a time in Add order,
    as a step of the same grace period named "run <name>". When the grace
    period ends first, Run returns at once with an ErrStopTimeout error naming
    the step still running (a Stop or a Run) and those never waited for.
    A clean shutdown returns nil; otherwise the start error or the first Run's
    error (unless it is the run ctx's own cancellation error), the later Run
    errors and every stop error, errors.Join, each naming its component.
    A nil ctx is context.Background(). A second Run returns ErrClosed. A Start
    that calls runtime.Goexit ends Run's goroutine, as it would any caller.

=== package pool
package pool // import "github.com/CrimsonCoder42/toolbench/pool"

Package pool is a long-lived worker pool (competing consumers): New starts a
fixed number of workers that take values from one queue and call fn on each;
Submit hands a value to the pool and blocks while the queue is full
(backpressure, never a drop); Close stops accepting, lets the workers finish
every accepted value and waits for them. The workers run in a group.Group,
so a panic in fn is recovered and returned as panics.ErrPanic, and with
WithFailFast the first error cancels the pool. By default every error is kept
and Close returns them joined (errors.Join). Nothing here panics on input:
a nil ctx is context.Background(), a non-positive worker count is ErrWorkers,
Submit after Close is ErrClosed. A worker may feed its own pool: Submit with the
ctx fn received never blocks (ErrQueueFull when there is no room), and TrySubmit
is that form from anywhere; WithOnDone reports progress; WithMaxErrors bounds
the errors kept.

For a fixed batch of tasks use group (fork-join) or parallel (Map, Filter,
ForEach); pool is for values that arrive over time and are processed by the same
bounded set of workers.

ID short form: POOL (IDs are TB-POOL-NNN).

Exports:

    TB-POOL-002  New           starts a Pool of workers calling fn on each submitted value

    TB-POOL-004  WithQueue     how many submitted values may wait for a worker (default 0: direct hand-off)

func WithFailFast() Option

    the pool's context: workers stop after their current fn call, Submit

    pkg.go.dev golang.org/x/sync/errgroup v0.25.0, "func WithContext" Tags:

func WithMaxErrors(n int) Option
    WithMaxErrors bounds the errors kept in collect mode: the first n fn
    errors (completion order) are kept, the rest are counted and the last
    of them remembered, and Close joins the kept ones with one error "pool:
    N further errors not kept" that wraps that last dropped error, so errors.Is
    still matches it. The default, and any n <= 0, keeps every error (the
    behaviour before this option: memory then grows one entry per failing value,
    bounded by the values submitted). It has no effect with WithFailFast,

func WithOnDone(f func(done, total int)) Option
    WithOnDone sets a progress hook called after each value's fn returns,
    whether it succeeded, returned an error or panicked, with done,
    the number of values finished so far (this one included), and total,
    the number accepted so far by Submit and TrySubmit. Both come from the
    pool's own atomic counters, never from a field the caller reads unguarded;
    a Submit in flight is counted in total a moment before it returns, so done
    <= total always holds. f runs on the worker's goroutine, outside every lock,
    possibly from many workers at once, so it must be safe for concurrent use
    and should not block (the worker waits for it). A panic in f is recovered
    and recorded as that value's error (panics.ErrPanic, joined with fn's error
    when both failed). f is not called for a value Submit refused nor for a
    value left unrun by a cancelled pool. f must not call Close (it would wait
    for itself). The default, and a nil f, is no hook.

    ID: TB-POOL-010 Pattern: observer (progress hook) Authority: Gamma et al.,
    Design Patterns, Addison-Wesley, 1994, "Observer" Tags: pool, options,
    progress, observability, hook

func WithQueue(n int) Option

type Pool[T any] struct {
	// Has unexported fields.
}
    Pool is a worker pool: a fixed set of workers, started by New, competing
    for values on one bounded queue and calling fn on each. Submit adds a value
    and blocks while the queue is full; Close stops accepting, waits until every
    accepted value has been run (or the pool's ctx has ended) and returns the

    and TrySubmit is the same non-blocking form from anywhere. WithOnDone

    ErrClosed, Close returns nil). A Pool must not be copied.

func (p *Pool[T]) Close() error
    Close stops the pool accepting values (a Submit blocked on a full queue
    returns ErrClosed), lets the workers run every value already accepted,
    waits until they have all exited and returns the errors. By default it
    returns every fn error and recovered panic joined with errors.Join (nil when
    there were none); with WithFailFast it returns the first. If the pool's ctx
    ended before the queue was empty, the values left unrun are reported as an
    error that wraps context.Cause of the pool's ctx, joined with the errors
    above (so errors.Is still matches the first error). With WithMaxErrors(n),
    when more than n errors occurred the kept ones are joined with one error
    "pool: N further errors not kept" that wraps the last dropped error.
    Close is idempotent: every call returns the first call's result. It must not
    be called from inside fn or the WithOnDone hook (it would wait for itself).

func (p *Pool[T]) Submit(ctx context.Context, v T) error
    Submit gives v to the pool. It returns nil once a worker or the queue
    has taken v; it blocks while every worker is busy and the queue is full
    (backpressure: nothing is dropped). It returns ErrClosed after Close has
    been called, context.Cause(ctx) when ctx is done, and context.Cause of the
    pool's ctx when the pool has stopped (New's ctx ended, or the first error
    with WithFailFast). A value for which Submit returned an error was not
    accepted. A nil ctx is context.Background(). Submit is safe for concurrent
    use, also with Close.

    From inside a worker of this pool, Submit does not block: called with the
    ctx fn received (or a child of it), it enqueues v when the queue has room
    (with no queue: when another worker is waiting) and otherwise returns
    ErrQueueFull, wrapped with the queue size; v was not accepted and is never
    run, so the caller handles the overflow (run it inline, keep it aside,
    or drop it knowingly). The two cases are told apart by the ctx: a worker
    that passes context.Background() (or any ctx not descended from its own)
    gets the blocking form, and then fn must not call Submit on its own pool
    without a queue to spare: with every worker inside fn it would wait until
    Close releases it with ErrClosed. TrySubmit is the non-blocking form from
    anywhere.

func (p *Pool[T]) TrySubmit(v T) (ok bool, err error)
    TrySubmit gives v to the pool without waiting: it returns (true, nil) once
    a worker or the queue has taken v, and (false, ErrQueueFull wrapped with the
    queue size) when there is no room (with no queue: no worker is waiting). It
    returns (false, ErrClosed) after Close has been called, for the zero value
    and for a nil *Pool, and (false, context.Cause of the pool's ctx) when the
    pool has stopped (New's ctx ended, or the first error with WithFailFast). A
    value for which ok is false was not accepted and is never run. TrySubmit is
    safe for concurrent use, also with Close, and may be called from inside fn.

    ID: TB-POOL-009 Pattern: worker pool (non-blocking submit) Authority:
    The Go Programming Language Specification, "Select statements" (a select
    with a default case never blocks), go1.27 Authority: Hohpe & Woolf,
    Enterprise Integration Patterns, Addison-Wesley, 2003, "Competing Consumers"
    Goroutines: none Cancel: the pool's ctx done: returns (false, its cause)
    Errors: ErrQueueFull (wrapped with the queue size) when full; ErrClosed
    after Close; the pool ctx's cause when it stopped Blocking: never Tags:
    concurrency, workers, pool, queue, non-blocking

=== package retry
package retry // import "github.com/CrimsonCoder42/toolbench/retry"

Package retry calls a function again when it fails, waiting between attempts
by a capped exponential backoff with jitter. Do and DoValue make at most
WithAttempts attempts (default 3), wait the delay a Backoff gives (default
FullJitter, base 100 ms, max 10 s) on a clock.Clock (WithClock), stop at once
on an error marked Permanent or one WithRetryIf rejects (by default a context
error and panics.ErrPanic), and return ErrExhausted wrapping the last error when
every attempt failed. WithAttemptTimeout bounds each attempt; WithMaxElapsed
caps the whole call without cutting an attempt in flight. Every call is bounded,
by attempts, by elapsed time or by ctx: there is no retry-forever setting,
at process start or anywhere else (a dependency that does not come up inside
the bounds makes the process exit non-zero, so the orchestrator restarts it).
The delays are calcbench algo/backoff (ALG-BACKOF-001..004), drawn from the
WithRand source. Retry only work that is safe to repeat (idempotent): a call
that failed after its side effect happened runs again.

ID short form: RETRY (IDs are TB-RETRY-NNN).

Exports:

    TB-RETRY-001  Do                  calls fn until it succeeds, an error stops it, or the attempts run out
    TB-RETRY-002  DoValue             Do for a function that returns a value
    TB-RETRY-003  Permanent           marks an error as not retryable; errors.Is and errors.As still see it
    TB-RETRY-004  ErrExhausted        every attempt failed; wraps the last attempt's error
    TB-RETRY-005  ErrAttemptTimeout   the cause of an attempt's ctx when WithAttemptTimeout expires
    TB-RETRY-006  Backoff             the delay between attempts: one calcbench backoff function, base and max
    TB-RETRY-007  Exponential         a Backoff of min(max, base·2^k), no jitter
    TB-RETRY-008  FullJitter          a Backoff of a uniform draw in [0, min(max, base·2^k))
    TB-RETRY-009  EqualJitter         a Backoff of half of min(max, base·2^k) plus a draw in the other half
    TB-RETRY-010  DecorrelatedJitter  a Backoff of min(max, a draw in [base, 3·previous delay))
    TB-RETRY-011  Option              configures Do and DoValue
    TB-RETRY-012  WithAttempts        sets the total number of attempts (default 3)
    TB-RETRY-013  WithBackoff         sets the Backoff (default FullJitter(100ms, 10s))
    TB-RETRY-014  WithAttemptTimeout  bounds each attempt; its ctx ends with ErrAttemptTimeout as the cause
    TB-RETRY-015  WithRetryIf         decides which errors are retried (default: all but context errors and ErrPanic)
    TB-RETRY-016  WithOnRetry         calls a function before each wait with the attempt, its error and the wait
    TB-RETRY-017  WithClock           sets the clock the waits and attempt timeouts use (default clock.Real)
    TB-RETRY-018  WithRand            sets the random source of the jitter draws (default math/rand/v2's top-level source)

func Do(ctx context.Context, fn func(context.Context) error, opts ...Option) error
    Do calls fn, on the calling goroutine, until it returns nil, returns an
    error that is not retried, ctx is done, or WithAttempts attempts (default
    3) have failed. Between attempts it waits the Backoff's delay (default
    FullJitter(100ms, 10s)) on the WithClock clock. Every call is bounded:
    by WithAttempts (default 3; WithAttempts(0) is that default, never
    "forever"), by WithMaxElapsed, or by ctx; there is no retry-forever setting,
    at process start or anywhere else (ExampleDo_startupDependency). A nil ctx
    is context.Background(); a nil fn is a panic in fn (panics.ErrPanic).

    ID: TB-RETRY-001 Pattern: retry with capped exponential backoff and jitter

    2024, "Retry strategies" Authority: Brooker, "Exponential Backoff And
    Jitter", AWS Architecture Blog, 2015, "Adding Jitter" Authority: Nygard,
    Release It!, 2nd ed., Pragmatic Bookshelf, 2018, ch.5 "Stability Patterns"
    (book, not opened) Goroutines: none; fn runs on the caller's goroutine

=== package pubsub
package pubsub // import "github.com/CrimsonCoder42/toolbench/pubsub"

Package pubsub is in-process publish-subscribe: a Bus delivers a copy of every
message published on a topic to each subscriber of that topic (Publish-Subscribe
Channel), by calling the subscriber's handler on the subscriber's own goroutine
(Event-Driven Consumer). Publisher and Subscriber are the two small interfaces
the Bus implements and that later packages (jobs, outbox) and the adapters
(Redis, Kafka, RabbitMQ) implement for an outside broker.

Delivery is AT-MOST-ONCE inside the process: a message reaches each subscriber
registered when it is published at most once, and is lost when the subscriber
leaves (ctx cancelled, handler error, Close) before handling it; those losses
are never silent: Subscribe's error counts them, and WithDropOldest reports
each message it drops. A slow subscriber slows Publish (backpressure) unless
WithDropOldest is passed. Every subscriber of a topic sees that topic's messages
in the same order. The Bus starts no goroutine: Subscribe runs its loop on the
caller's goroutine and returns when its ctx is done, the Bus is closed or the
handler fails, with the handler finished. A panic in a handler is returned as
panics.ErrPanic. Nothing panics on input.

ID short form: PUBSUB (IDs are TB-PUBSUB-NNN).

Exports:

    TB-PUBSUB-002  Subscriber         calls a handler for each message on a topic until ctx is done (the interface the Bus and broker adapters implement)

TYPES

type Bus[M any] struct {
	// Has unexported fields.
}
    Bus is an in-process publish-subscribe channel: Publish delivers a copy of
    each message to every subscriber registered on its topic when the message
    is published, and Subscribe calls a handler for each message of its topic
    on the caller's goroutine. It implements Publisher and Subscriber. Delivery
    is at-most-once: a message is lost for a subscriber that leaves before
    handling it (counted in that Subscribe's error) or, with WithDropOldest,
    that falls behind (reported). Publish with no subscriber on the topic
    delivers nothing and returns nil. Every subscriber of a topic sees that
    topic's messages in one order, the order Publish calls were admitted,
    each call's messages consecutively. Topics are independent and created on
    first Subscribe. The zero value is ready to use (no buffer, backpressure,
    no hook); NewBus sets options. A Bus must not be copied after first use.

    ID: TB-PUBSUB-003 Pattern: publish-subscribe channel (event-driven
    consumers) Authority: Hohpe & Woolf, Enterprise Integration Patterns,
    Addison-Wesley, 2003, "Publish-Subscribe Channel" Authority: Hohpe & Woolf,
    Enterprise Integration Patterns, Addison-Wesley, 2003, "Event-Driven
    Consumer" Goroutines: none; Subscribe runs on the caller's goroutine and
    has returned, its handler finished, when it returns Cancel: Publish returns
    context.Cause(ctx) when its ctx ends while it waits (messages already
    handed over stay delivered); Subscribe returns context.Cause(ctx) after its
    current handler call Errors: ErrClosed after Close; ErrInvalid for a nil
    handler or invalid options; ErrSlowSubscriber for a subscriber evicted by
    WithDropSubscriber; a handler error or panic (panics.ErrPanic) ends that
    Subscribe and is returned Blocking: Publish blocks while a subscriber of the
    topic is busy and its buffer is full (backpressure), unless WithDropOldest
    or WithDropSubscriber; Subscribe blocks for the whole subscription Math:
    ALG-QUEUE-002 CircularBuffer (WithDropOldest only) Tags: concurrency,
    pubsub, messaging, fan-out, backpressure, panic

func NewBus[M any](opts ...Option[M]) *Bus[M]
    NewBus returns a Bus configured by opts. A nil Option is ignored. WithBuffer
    above 2^20 does not panic: the Bus is returned and its Publish and Subscribe
    return ErrInvalid naming the option.

    ID: TB-PUBSUB-004 Pattern: publish-subscribe channel (constructor)
    Authority: Hohpe & Woolf, Enterprise Integration Patterns, Addison-Wesley,
    2003, "Publish-Subscribe Channel" Blocking: never Tags: pubsub, constructor

func (b *Bus[M]) Close() error
    Close closes the Bus: Publish and Subscribe return ErrClosed from now on,
    a Publish waiting on a subscriber returns ErrClosed, and every running
    Subscribe's ctx is cancelled with cause ErrClosed, so each returns ErrClosed
    once its current handler call has returned (Close does not wait for that:
    the Subscribe callers own their goroutines). Messages still buffered are not
    delivered and are counted in each Subscribe's error. Close always returns
    nil; calling it again, or on the zero value or a nil *Bus, is a no-op.
    It may be called from a handler.

func (b *Bus[M]) Publish(ctx context.Context, topic string, msgs ...M) error
    Publish delivers msgs, in order, to every subscriber registered on topic,
    each message to all of them before the next. It returns nil once every
    subscriber has taken (or buffered) every message; with no subscriber
    on topic, or no msgs, it delivers nothing and returns nil. It blocks
    while a subscriber is busy and its buffer is full (backpressure), unless
    WithDropOldest (drops its oldest message) or WithDropSubscriber (evicts
    it with cause ErrSlowSubscriber); a subscriber that leaves while Publish
    waits on it, or was evicted, is skipped. Concurrent Publish calls on one
    topic take turns (one order for every subscriber); different topics never
    wait for each other. It returns ErrClosed after Close (also while waiting),
    context.Cause(ctx) when ctx ends first, ErrInvalid for invalid options, and
    a panic in a WithDropOldest or WithDropSubscriber report as panics.ErrPanic;
    on an error the messages already handed over stay delivered and the rest are
    not published. A nil ctx is context.Background(). Safe for concurrent use,
    also from a handler (on another topic, or with buffer to spare: a handler
    publishing to its own full, unbuffered topic waits for itself).

func (b *Bus[M]) Subscribe(ctx context.Context, topic string, h func(context.Context, M) error) (err error)
    Subscribe registers h on topic and calls it for each message published
    there from then on, one at a time on the calling goroutine, in the
    topic's order, with a ctx that is cancelled when ctx is or when the Bus
    closes (cause ErrClosed). It blocks until that ctx is done or h returns
    an error, and returns after h has returned; it never returns nil.
    The result is context.Cause(ctx), ErrClosed, ErrSlowSubscriber (evicted by
    WithDropSubscriber), h's error, a panic in h or in a WithOnDelivered hook as
    panics.ErrPanic; when messages were left in this subscriber's buffer (lost:
    at-most-once) it is wrapped as "pubsub: N buffered messages not delivered:
    <reason>", so errors.Is still matches the reason. Unsubscribe by cancelling
    ctx. It returns at once ErrClosed on a closed Bus, ErrInvalid for a nil
    h or invalid options, and context.Cause(ctx) when ctx is already done.
    A nil ctx is context.Background(). Safe for concurrent use; one topic may
    have any number of subscribers, each with its own buffer.

type Message[T any] struct {
	Headers map[string]string // read-only once published; nil = no headers
	Body    T
}
    Message is the envelope a payload travels in: Headers for what the messaging
    system and its middleware read (ids, routing, tracing), Body for the data,
    carried as-is. It is the agreed type the Bus, the broker adapters and
    the packages built on them speak, so a correlation or request id crosses
    a process boundary in the headers and never inside the payload. The Bus
    delivers it by value and never reads Headers; the map is SHARED read-only
    among a topic's subscribers, so a handler must not mutate m.Headers:
    it calls WithHeader, which returns a copy. The zero value is ready to use:
    nil Headers means no headers (Header reports false, WithHeader makes a
    one-entry map). Message[T] is a plain value: no goroutines, nothing blocks,
    nothing fails.

    ID: TB-PUBSUB-011 Pattern: message (envelope: header + body) Authority:
    Hohpe & Woolf, Enterprise Integration Patterns, Addison-Wesley, 2003,
    "Message" Authority: Hohpe & Woolf, Enterprise Integration Patterns,
    Addison-Wesley, 2003, "Correlation Identifier" Tags: pubsub, messaging,
    envelope, headers, correlation

func (m Message[T]) Header(key string) (string, bool)

    (Publish and Subscribe return ErrInvalid). Each Subscribe allocates its own
    buffer.

func WithDropOldest[M any](report func(topic string, m M)) Option[M]
    WithDropOldest makes a full subscriber buffer drop its oldest message to
    take the new one, instead of blocking Publish: a slow subscriber then loses
    its oldest messages and never slows the publisher. Each dropped message
    is passed to report(topic, m) on the publishing goroutine, after the new
    message has been buffered and outside every lock. report must not block for
    long and must not Publish on the same topic (that Publish would wait for
    the one calling report). A nil report drops without reporting, which the
    caller has then chosen explicitly. The buffer is WithBuffer's n, at least 1
    (WithDropOldest with no buffer keeps the newest message only). M is inferred
    from report and must be the Bus's message type (checked by the compiler).
    A panic in report is returned by Publish as panics.ErrPanic. The three
    slow-subscriber policies (backpressure, WithDropOldest, WithDropSubscriber)
    are mutually exclusive: the last one passed to NewBus wins.

    ID: TB-PUBSUB-007 Pattern: ring buffer with overwrite (drop oldest)
    Authority: Hohpe & Woolf, Enterprise Integration Patterns, Addison-Wesley,

func WithDropSubscriber[M any](report func(topic string, m M)) Option[M]

    which the caller has then chosen explicitly. The buffer is WithBuffer's n,
    at least 1: with no buffer "full" would mean "the handler is between two
    messages", so one slot is kept, as WithDropOldest does. M is inferred from

    by Publish as panics.ErrPanic; the eviction has happened. The three
    slow-subscriber policies (backpressure, WithDropOldest, WithDropSubscriber)

type Publisher[M any] interface {
	Publish(ctx context.Context, topic string, msgs ...M) error
}
    Publisher publishes messages on a topic. It is the one method a message
    producer needs; the in-process Bus implements it, and so do the broker
    adapters (adapters/redis, adapters/kafka, adapters/rabbitmq) and the
    packages built on them. Publish returns nil once every message has been
    handed to the channel (for the Bus: to every subscriber registered on topic,

type Subscriber[M any] interface {
	Subscribe(ctx context.Context, topic string, h func(context.Context, M) error) error
}
    Subscriber calls h for each message on topic, one at a time, in the
    channel's order, until ctx is done, the channel closes or h returns an
    error. It blocks for the whole subscription and returns the reason it ended,
    never nil: context.Cause(ctx), ErrClosed, or h's error (a panic in h as
    panics.ErrPanic), always after h has returned. Unsubscribing is cancelling
    ctx. The in-process Bus implements it, and so do the broker adapters.
    What happens to a message whose h failed (lost, redelivered, dead-lettered)
    is the implementation's documented choice; for the Bus it is lost
    (at-most-once).

    Addison-Wesley, 2003, "Event-Driven Consumer" Authority: Hohpe & Woolf,
    Enterprise Integration Patterns, Addison-Wesley, 2003, "Publish-Subscribe
    Channel" Tags: pubsub, messaging, interface, subscribe, consumer

=== package ctxkey
package ctxkey // import "github.com/CrimsonCoder42/toolbench/ctxkey"

Package ctxkey gives context values a typed key that cannot collide with another
package's key: one package-level variable replaces the unexported key type,
the two accessor functions and the type assertion that the context documentation
asks every user of context.WithValue to write.

ID short form: CTXKEY (IDs are TB-CTXKEY-NNN).

Exports:

    TB-CTXKEY-001  Key  a typed context key: With stores a T, Value reads it back as (T, bool)
    TB-CTXKEY-002  New  returns a new, distinct key with a name used only for printing
    TB-CTXKEY-003  RequestID  the one key every toolbench package uses for the request / correlation id
    TB-CTXKEY-004  MaxRequestIDLen  the longest request id ValidRequestID accepts: 128 bytes
    TB-CTXKEY-005  ErrRequestID  the sentinel WithRequestID wraps for an empty, too long or non-printable id
    TB-CTXKEY-006  NewRequestID  a fresh request id from crypto/rand.Text (26 base32 characters, >= 128 bits)
    TB-CTXKEY-007  ValidRequestID  reports whether s is 1..128 bytes of printable ASCII 0x21-0x7E
    TB-CTXKEY-008  WithRequestID  validates id and stores it under RequestID, or returns ctx unchanged and ErrRequestID
    TB-CTXKEY-009  RequestIDFrom  the request id stored in ctx as (string, bool)
    TB-CTXKEY-010  EnsureRequestID  the stored valid request id, or a fresh one stored in a child context

CONSTANTS

const MaxRequestIDLen = 128
    MaxRequestIDLen is the longest request id, in bytes, that ValidRequestID
    accepts and WithRequestID stores: 128. A UUID (36), a W3C traceparent (55)
    and a host-counter id fit with margin; a 10 KB inbound header does not and
    is rejected rather than stored, logged or echoed.

    ID: TB-CTXKEY-004 Pattern: bounded input (default bound) Authority:
    RFC 9110, HTTP Semantics, 2022, §5.5 "Field Values" Tags: request-id, bound,
    default


VARIABLES

var ErrRequestID = errors.New("ctxkey: invalid request id")
    ErrRequestID is returned, wrapped, by WithRequestID when the id is empty,
    longer than MaxRequestIDLen or holds a byte outside printable ASCII
    0x21-0x7E; the context was not changed. The wrapped message names the reason
    and the byte length, never the id's bytes, so logging the error cannot forge
    a log line. Match it with errors.Is.

    ID: TB-CTXKEY-005 Pattern: sentinel error Authority: RFC 9110, HTTP
    Semantics, 2022, §5.5 "Field Values" (CR, LF and NUL in a field value are
    invalid and dangerous) Tags: request-id, error, sentinel, validation

var RequestID = New[string]("ctxkey.request-id")
    RequestID is the one key every toolbench package uses for the request /
    correlation id: logging reads it (logging.FromKey), message headers and HTTP
    and gRPC middleware carry the same value, so one id joins every log line,
    reply and message of one request. A request id is an opaque string of 1 to
    MaxRequestIDLen bytes, every byte printable ASCII (0x21-0x7E: no space,
    no control character, no CR/LF/NUL, no DEL, no non-ASCII), so it passes a
    header, a log line and a message header unchanged. An inbound id (an HTTP
    header, a message header) is attacker text: store it through WithRequestID,
    which validates, never through RequestID.With directly; EnsureRequestID
    replaces a stored id that does not pass ValidRequestID. The key is immutable
    and safe for concurrent use; it prints as "ctxkey.request-id".

    ID: TB-CTXKEY-003 Pattern: correlation identifier (typed context key)
    Authority: Hohpe & Woolf, Enterprise Integration Patterns, Addison-Wesley,
    2003, "Correlation Identifier" Authority: pkg.go.dev, package context,
    "func WithValue", go1.27 Tags: context, request-id, correlation-id, key


FUNCTIONS

func EnsureRequestID(ctx context.Context) (context.Context, string)
    EnsureRequestID returns ctx and its request id when ctx already holds one
    that passes ValidRequestID, allocating nothing; otherwise (no id, or a
    stored id that is not valid) it mints one with NewRequestID, stores it under
    RequestID in a child of ctx and returns that child and the id. A nil ctx is
    treated as context.Background. It never fails: a middleware calls it once
    at the boundary and every later read sees the same id. Starts no goroutine,
    never blocks, never panics.

    ID: TB-CTXKEY-010 Pattern: correlation identifier (get-or-create at the
    boundary) Authority: Hohpe & Woolf, Enterprise Integration Patterns,
    Addison-Wesley, 2003, "Correlation Identifier" Authority: pkg.go.dev,
    package crypto/rand, "func Text", go1.24 Tags: request-id, correlation-id,
    context, middleware

func NewRequestID() string
    NewRequestID returns a fresh request id: crypto/rand.Text, 26 characters
    of the RFC 4648 base32 alphabet (A-Z, 2-7) carrying at least 128 bits
    of randomness, so ids are distinct with vanishing collision probability
    and never guessable. Every id it returns passes ValidRequestID and fits
    a header, a URL and a log line without escaping. There is no seed,
    no counter and no shared state: call it from any goroutine. It is the choice
    over a UUID because an id is not mathematics (calcbench has no identifier
    primitive) and the standard library's Text is shorter and carries no
    version semantics; a consumer that must emit a UUID stores its own through
    WithRequestID.

    ID: TB-CTXKEY-006 Pattern: correlation identifier (generation) Authority:
    Hohpe & Woolf, Enterprise Integration Patterns, Addison-Wesley, 2003,
    "Correlation Identifier" Authority: pkg.go.dev, package crypto/rand,
    "func Text", go1.24 Errors: none: crypto/rand never returns an error;
    an unusable OS random source crashes the program by that package's contract,
    never a weak id Blocking: none (one read of the OS random source) Tags:
    request-id, correlation-id, random, generator

func RequestIDFrom(ctx context.Context) (string, bool)
    RequestIDFrom returns the request id stored under RequestID in ctx and true,
    or "" and false when none is stored or ctx is nil. It returns what is
    stored, even an id placed by RequestID.With without validation; a caller
    forwarding the id to a header uses EnsureRequestID, which replaces an
    invalid one. Never blocks.

    ID: TB-CTXKEY-009 Pattern: correlation identifier (typed read) Authority:
    Hohpe & Woolf, Enterprise Integration Patterns, Addison-Wesley, 2003,
    "Correlation Identifier" Authority: pkg.go.dev, package context, "type
    Context" (method Value), go1.27 Tags: request-id, correlation-id, context,
    read

func ValidRequestID(s string) bool
    ValidRequestID reports whether s is a request id this package stores and
    forwards: not empty, at most MaxRequestIDLen bytes, and every byte in
    0x21-0x7E (printable ASCII: no space, no tab, no CR, LF or NUL, no DEL, no
    non-ASCII byte). The check is byte-wise, so any multi-byte rune is rejected.
    Call it on every inbound id (an HTTP header, a message header, a query
    parameter) before the id reaches a log or a context. Pure, no allocation;
    the length is checked before the bytes, so a huge input costs one compare.

    ID: TB-CTXKEY-007 Pattern: input validation (allow-list) Authority:
    RFC 9110, HTTP Semantics, 2022, §5.5 "Field Values" (visible ASCII; CR,
    LF and NUL are invalid and dangerous) Tags: request-id, validation, header,
    log-forging

func WithRequestID(ctx context.Context, id string) (context.Context, error)
    WithRequestID stores id under RequestID in a child of ctx after validating
    it with ValidRequestID. An invalid id (empty, over MaxRequestIDLen,
    a byte outside 0x21-0x7E) returns ctx unchanged and ErrRequestID wrapped
    with the reason and the byte length (never the bytes): nothing is stored,
    so an attacker's header is neither logged nor echoed. A nil ctx is treated
    as context.Background on both paths, so the returned context is never nil.
    Starts no goroutine, never blocks, never panics.

    ID: TB-CTXKEY-008 Pattern: correlation identifier (validated store)
    Authority: Hohpe & Woolf, Enterprise Integration Patterns, Addison-Wesley,
    2003, "Correlation Identifier" Authority: RFC 9110, HTTP Semantics,
    2022, §5.5 "Field Values" Errors: ErrRequestID (wrapped) when id fails
    ValidRequestID; ctx is returned unchanged Tags: request-id, correlation-id,
    context, validation


TYPES

type Key[T any] struct {
	// Has unexported fields.
}
    Key is a typed key for a request-scoped value of type T carried in a
    context.Context.

    The key's identity is its pointer: two keys made by two New calls are
    distinct even when their names and types are equal, so a value stored under
    one is never seen through the other, and no key can ever equal a string
    or any other built-in key another package uses. Key has a string field,
    so it is never zero-size and two keys never share an address. A Key is
    immutable and safe for concurrent use. Create it with New and keep it in a
    package-level variable; the zero value used through a pointer is a valid key
    with the empty name, and copying a Key makes a different key.

    ID: TB-CTXKEY-001 Pattern: typed context key (type-safe accessors for
    request-scoped values) Authority: pkg.go.dev, package context, "func
    WithValue" and "type Context" (method Value), go1.27 Authority: Ajmani,
    "Go Concurrency Patterns: Context", The Go Blog, 2014, "Example: Google Web
    Search" Tags: context, request-scoped, type-safe, key

func New[T any](name string) *Key[T]
    New returns a new key for values of type T. The name is shown when the key
    or a context holding it is printed and is never part of the key's identity:
    New[int]("user") twice gives two distinct keys. Callers namespace the name
    ("auth.user-id") so printed contexts stay readable.

    ID: TB-CTXKEY-002 Pattern: typed context key (type-safe accessors for
    request-scoped values) Authority: pkg.go.dev, package context, "func
    WithValue" and "type Context" (method Value), go1.27 Authority: Ajmani,
    "Go Concurrency Patterns: Context", The Go Blog, 2014, "Example: Google Web
    Search" Tags: context, request-scoped, type-safe, key, constructor

func (k *Key[T]) String() string
    String returns the key's name, so fmt.Sprint of a context shows it, as in
    "context.Background.WithValue(user-id, int)". A nil k prints "<nil>".

func (k *Key[T]) Value(ctx context.Context) (T, bool)
    Value returns the value k holds in ctx (the nearest one, walking from ctx to
    its root) and true, or the zero value of T and false when k holds nothing
    there. A stored nil (for example a nil error) reads back as (nil, true).
    A nil ctx or a nil k gives (zero, false). Value never blocks.

func (k *Key[T]) With(ctx context.Context, v T) context.Context
    With returns a child of ctx in which k holds v; ctx itself is not changed.
    A later With on the same key in a descendant context shadows v for that
    descendant only. A nil ctx is treated as context.Background() (the standard
    library panics there; a toolbench function never panics on input). On a nil
    k, With stores nothing and returns ctx unchanged. With starts no goroutine
    and never blocks; cancellation is ctx's.

=== package group
package group // import "github.com/CrimsonCoder42/toolbench/group"

Package group runs a set of functions on their own goroutines and waits for
all of them: the error group (golang.org/x/sync/errgroup's shape: Go, TryGo,
SetLimit, Wait, WithContext) and the result group (typed results in submission
order). The first error wins and cancels the derived context; Wait returns only
after every started goroutine has returned. A panic in a function is recovered
and returned through Wait as panics.ErrPanic with its stack, never re-raised
and never a crash. Nothing here panics or deadlocks on input: SetLimit while
goroutines are active applies to later calls, and a limit of zero is reported
as ErrZeroLimit. SetCollect (Group) and WithCollect (Results) are the opt-in to
keep every error joined with errors.Join; Results then returns partial values
with the zero value in a failed slot.

ID short form: GROUP (IDs are TB-GROUP-NNN).

Exports:

    TB-GROUP-001  Group         an error group: first error wins and cancels, optional limit, panics become ErrPanic
    TB-GROUP-002  WithContext   a new Group and a ctx cancelled on its first error or when Wait returns
    TB-GROUP-003  Results       a result group: one value per Go, returned by Wait in submission order
    TB-GROUP-004  NewResults    a Results bound to a ctx, with options
    TB-GROUP-005  Option        a functional option for NewResults
    TB-GROUP-006  WithLimit     the most goroutines a Results runs at once (default no limit)
    TB-GROUP-007  ErrZeroLimit  the error recorded when Go is called while the limit is zero
    TB-GROUP-008  Group.SetCollect  Wait returns every error joined with errors.Join, completion order (default: first only)
    TB-GROUP-009  WithCollect   Results option: Wait returns partial values (zero in a failed slot) and every error joined

VARIABLES

var ErrZeroLimit = errors.New("group: limit is zero: no goroutine can be started")
    ErrZeroLimit is recorded as the group's error when Go is called, or is
    waiting for a slot, while the limit is zero. errgroup's Go blocks forever
    in that case; here fn is not started, Go returns at once and Wait reports
    ErrZeroLimit (first error wins, so an earlier error is kept).

    ID: TB-GROUP-007 Pattern: error group (sentinel error) Authority: pkg.go.dev
    golang.org/x/sync/errgroup v0.25.0, "func (*Group) SetLimit" Tags:
    concurrency, errgroup, limit, sentinel


TYPES

type Group struct {
	// Has unexported fields.
}
    Group runs functions on their own goroutines and waits for them; the first
    non-nil error is kept and, for a Group made by WithContext, cancels its
    context. It mirrors golang.org/x/sync/errgroup.Group, except that a panic
    in a function is recovered and returned by Wait as *panics.PanicError
    (errors.Is(err, panics.ErrPanic)), SetLimit never panics, and Go with
    a limit of zero records ErrZeroLimit instead of blocking forever.
    runtime.Goexit in a function is not an error: its goroutine ends and Wait
    does not hang. The zero value is ready to use: no limit, no cancel on error.
    A Group must not be copied after first use and is meant for one task.

    ID: TB-GROUP-001 Pattern: error group (fork-join, first error
    cancels) Authority: pkg.go.dev golang.org/x/sync/errgroup v0.25.0,
    "type Group" Authority: Cox-Buday, Concurrency in Go, O'Reilly, 2017,
    ch.4 "Error Handling" Goroutines: one per started Go or TryGo; each ends
    when its function returns; all have exited when Wait returns Cancel:
    WithContext's ctx is cancelled with the first error as its cause, or when
    Wait returns Errors: the first of: a function's error, a recovered panic
    (panics.ErrPanic), ErrZeroLimit; every one joined with SetCollect(true)
    Blocking: Go blocks while the active count is at the limit; TryGo never
    blocks; Wait blocks until all return Tags: concurrency, errgroup, cancel,
    limit, panic

func WithContext(ctx context.Context) (*Group, context.Context)
    WithContext returns a new Group and a context derived from ctx. The derived
    context is cancelled the first time a function passed to Go returns a
    non-nil error (or panics), with that error as its cause (context.Cause),
    or the first time Wait returns, whichever comes first. A nil ctx is
    context.Background().

    ID: TB-GROUP-002 Pattern: error group (fork-join, first error cancels)
    Authority: pkg.go.dev golang.org/x/sync/errgroup v0.25.0, "func WithContext"
    Goroutines: none Cancel: the returned ctx is done when ctx is, on the
    group's first error, or when Wait returns Tags: concurrency, errgroup,
    context, cancel

func (g *Group) Go(fn func() error)
    Go calls fn on a new goroutine. It blocks until the goroutine can start
    without the number of active goroutines exceeding the limit. If the limit is
    zero, fn is not started and ErrZeroLimit is recorded. The first fn to return
    a non-nil error or to panic sets the error Wait returns and cancels the
    Group's context. As with errgroup, the first call to Go must happen before
    Wait; fn may call Go on its own Group. A nil fn is a panic of the call and
    is returned as panics.ErrPanic.

func (g *Group) SetCollect(collect bool)
    SetCollect chooses what Wait returns when more than one function fails. With
    collect true, every function error, every recovered panic (panics.ErrPanic)
    and ErrZeroLimit are kept, one entry per failed Go or TryGo in the order
    they completed, and Wait returns them joined with errors.Join (nil when none
    failed; a single failure is still wrapped by Join, so match with errors.Is
    or errors.As, never ==). With false, the default, Wait returns the first
    error only, as errgroup. Collecting changes what Wait returns, not when the
    group stops: the first error still cancels a WithContext ctx with itself
    as the cause; a caller who wants every function to run to completion uses
    a Group without a ctx (the zero Group does not cancel on error). Call it
    before the first Go, as errgroup says of SetLimit; a later call applies to
    errors recorded afterwards, and a first error recorded before it is still
    the first entry of the join.

    ID: TB-GROUP-008 Pattern: error group (collect-all errors) Authority:
    pkg.go.dev errors, "func Join", go1.27 Authority: pkg.go.dev
    golang.org/x/sync/errgroup v0.25.0, "func (*Group) SetLimit" Goroutines:
    none Errors: with collect true Wait returns errors.Join of every error in
    completion order; false: the first only Blocking: none Tags: concurrency,
    errgroup, errors, join, collect

func (g *Group) SetLimit(n int)
    SetLimit limits the number of active goroutines to n. A negative n means
    no limit; zero means no goroutine can start (Go records ErrZeroLimit,
    TryGo returns false). Unlike errgroup it may be called while goroutines are
    active: running goroutines are not stopped, and the new limit applies to
    every later Go and TryGo, including a Go that is already waiting for a slot.

func (g *Group) TryGo(fn func() error) bool
    TryGo calls fn on a new goroutine only if the number of active goroutines
    is below the limit, and reports whether it started. With a limit of zero it
    returns false and records nothing (errgroup's rule).

func (g *Group) Wait() error
    Wait blocks until every function started by Go and TryGo has returned,
    then cancels the Group's context and returns the first error, or nil.
    After SetCollect(true) it returns every error joined with errors.Join,
    in completion order, the first error first.

type Option func(*config)
    Option changes how NewResults builds a Results. A nil Option is ignored.

    ID: TB-GROUP-005 Pattern: functional options Authority: pkg.go.dev
    golang.org/x/sync/errgroup v0.25.0, "func (*Group) SetLimit" Tags:
    concurrency, options

func WithCollect() Option
    WithCollect makes a Results keep partial results: Wait returns one value
    per Go in submission order, with the zero value in every slot whose
    function returned an error, panicked or was not called because the context
    was already done, and the error of every failure joined with errors.Join
    (Group.SetCollect underneath). The first error still cancels the context,
    so a function that has not started when it fires is not called and its
    slot holds the zero value with the context's cause in the join; a function
    already running that then succeeds keeps its value. Without the option Wait
    returns nil and the first error.

    ID: TB-GROUP-009 Pattern: result group (partial results, collect-all errors)
    Authority: pkg.go.dev errors, "func Join", go1.27 Authority: pkg.go.dev
    golang.org/x/sync/errgroup v0.25.0, "func (*Group) SetLimit" Errors:
    Wait returns the values of the Go calls that succeeded and errors.Join of
    every failure Tags: concurrency, errgroup, results, errors, join, options

func WithLimit(n int) Option
    WithLimit sets the most goroutines a Results runs at once, as Group.SetLimit
    before the first Go. A negative n (the default, -1) means no limit; zero
    means no goroutine can start and every Go records ErrZeroLimit.

    ID: TB-GROUP-006 Pattern: bounded parallelism (limit option) Authority:
    pkg.go.dev golang.org/x/sync/errgroup v0.25.0, "func (*Group) SetLimit"
    Tags: concurrency, limit, options

type Results[T any] struct {
	// Has unexported fields.
}
    Results runs functions that each produce one value on their own goroutines
    and returns the values in the order Go was called. It is a Group underneath:
    the first error (or recovered panic, panics.ErrPanic) wins and cancels
    the context passed to every function, and Wait returns only after every
    goroutine has returned. A function whose goroutine starts after the
    context is done is not called; context.Cause(ctx) is recorded instead,
    so a cancelled run is never reported as a success. The zero value is ready
    to use, with context.Background() and no limit; NewResults passes a context
    and options. A Results must not be copied after first use and is meant for
    one task.

    ID: TB-GROUP-003 Pattern: result group (fork-join with ordered results)
    Authority: pkg.go.dev golang.org/x/sync/errgroup v0.25.0, "type Group",
    "func WithContext" Authority: Cox-Buday, Concurrency in Go, O'Reilly, 2017,
    ch.4 "Error Handling" Goroutines: one per Go (at most the limit at once);
    all have exited when Wait returns Cancel: the ctx given to each function
    is cancelled on the first error, when the parent is, or when Wait returns
    Errors: the first of: a function's error, panics.ErrPanic, ErrZeroLimit,
    the context's cause; every one joined with WithCollect Blocking: Go blocks
    while the active count is at the limit; Wait blocks until all return Tags:
    concurrency, errgroup, results, ordered, generic

func NewResults[T any](ctx context.Context, opts ...Option) *Results[T]
    NewResults returns a Results whose functions receive a context derived from
    ctx (a nil ctx is context.Background()), configured by opts. The default is
    no limit.

    ID: TB-GROUP-004 Pattern: result group (fork-join with ordered results)
    Authority: pkg.go.dev golang.org/x/sync/errgroup v0.25.0, "func
    WithContext", "func (*Group) SetLimit" Goroutines: none Cancel: the derived
    ctx is done when ctx is, on the first error, or when Wait returns Tags:
    concurrency, errgroup, results, generic

func (r *Results[T]) Go(fn func(ctx context.Context) (T, error))
    Go reserves the next result slot and calls fn on a new goroutine with the
    Results' context. It blocks while the active count is at the limit. fn's
    value is kept only if fn returns a nil error. If the context is done when
    the goroutine starts, fn is not called and the context's cause is recorded.
    A nil fn is returned as panics.ErrPanic. As with Group, the first call to Go
    must happen before Wait.

func (r *Results[T]) Wait() ([]T, error)
    Wait blocks until every function has returned and cancels the context.
    With no error it returns one value per Go, in the order Go was called (nil
    if Go was never called); otherwise it returns nil and the first error.
    With WithCollect it returns the values in submission order, the zero value
    in every failed slot, and every error joined with errors.Join.
